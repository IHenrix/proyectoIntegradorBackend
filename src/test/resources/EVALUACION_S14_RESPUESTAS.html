Pregunta 1 — Escaneo Pasivo vs. Activo en OWASP ZAP

¿Cuál es la diferencia entre el escaneo pasivo y activo en OWASP ZAP? ¿Cuándo usarías cada uno?

Escaneo Pasivo:
ZAP analiza el tráfico HTTP que ya existe sin enviar ninguna petición adicional al servidor. Solo observa las peticiones y respuestas que el navegador genera naturalmente mientras se navega la aplicación.
  • No modifica, no ataca, no genera carga extra en el servidor.
  • Detecta: cabeceras de seguridad faltantes (X-Frame-Options, CSP), cookies sin flag Secure/HttpOnly, información sensible en respuestas (versiones de servidor), formularios sin CSRF token.
  • Cuándo usarlo: siempre, como primera etapa. Es seguro ejecutarlo incluso en ambientes de producción ya que no genera tráfico adicional.
Escaneo Activo:
ZAP envía payloads maliciosos deliberados a todos los parámetros encontrados (formularios, URLs, headers) para descubrir vulnerabilidades reales.
  • Genera muchas peticiones al servidor. Puede causar errores, registros falsos en BD, alertas de seguridad.
  • Detecta: SQL Injection, XSS (Cross-Site Scripting), Command Injection, Path Traversal, XXE, SSRF.
  • Cuándo usarlo: en ambientes de testing/staging, nunca en producción sin autorización explícita. Siempre después del escaneo pasivo.

Pregunta 2 — Ataque IDOR y su relación con A01

¿Qué es un ataque IDOR? ¿Cómo se relaciona con la categoría A01:2021 del OWASP Top 10?

IDOR (Insecure Direct Object Reference — Referencia Directa Insegura a Objetos):
Es un tipo de vulnerabilidad donde una aplicación expone identificadores internos de objetos (IDs de base de datos, nombres de archivo, etc.) en URLs o parámetros, y un atacante puede manipularlos para acceder a recursos que no le pertenecen.

Ejemplo clásico: 
// URL normal del usuario A:
GET /api/historial/42   → muestra su historial (id=42)

// El atacante cambia el número:
GET /api/historial/43   → si no hay validación, muestra el historial del usuario B
Relación con A01:2021 (Broken Access Control):
IDOR es una de las manifestaciones más comunes de A01. La raíz del problema es la misma: la aplicación no verifica que el recurso solicitado pertenezca al usuario que hace la petición. A01 es la categoría más amplia que cubre todos los fallos de control de acceso; IDOR es el mecanismo específico de ataque que los explota.

Cómo PasajeYá previene IDOR:
En lugar de exponer IDs en la URL, el email del usuario siempre viene del JWT: 
// AlertaController.java — el email viene del TOKEN, no de la URL
@GetMapping
public ResponseEntity<List<AlertaDTO>> listar(Authentication auth) {
    return ResponseEntity.ok(alertaService.listar(auth.getName())); // email del JWT
}

// NO existe un endpoint como:
// GET /api/alertas/{usuarioId}   ← esto sería vulnerable a IDOR
Un atacante no puede cambiar su email en el JWT sin invalidar la firma HMAC-SHA, por lo que es imposible suplantar a otro usuario.

Pregunta 3 — Por qué MD5 no debe usarse para contraseñas en 2025

¿Por qué MD5 no debe usarse para hashear contraseñas en 2025? ¿Cuál es la alternativa recomendada en Java?

Razones por las que MD5 es inseguro para contraseñas:
  1. Sin salt: MD5 es determinista — la misma entrada produce siempre el mismo hash. Esto permite rainbow tables: tablas precomputadas que mapean miles de millones de contraseñas comunes a sus hashes MD5. Basta con buscar el hash en la tabla para recuperar la contraseña.
  2. Velocidad excesiva: MD5 fue diseñado para ser rápido. Con una GPU moderna se pueden calcular más de 10,000 millones de hashes MD5 por segundo. Un atacante con la BD puede hacer fuerza bruta de contraseñas de 8 caracteres en minutos.
  3. Colisiones conocidas: MD5 tiene colisiones documentadas desde 2004 — dos entradas distintas producen el mismo hash. Aunque menos relevante para contraseñas, confirma que el algoritmo es criptográficamente débil.
  4. No es un KDF: MD5 es una función de hash de propósito general, no una Key Derivation Function (KDF). Las KDF están diseñadas específicamente para derivar claves/hashes de contraseñas con mecanismos de lentitud ajustable.
Alternativa recomendada en Java — BCrypt: 
// Dependencia (spring-boot-starter-security la incluye):
// org.springframework.security:spring-security-crypto

// PasajeYá — SecurityConfig.java:
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();  // factor de trabajo por defecto: 10
}

// Ventajas de BCrypt:
// 1. Salt automático — cada hash es único, rainbow tables inútiles
// 2. Factor de trabajo configurable — se puede hacer más lento en el futuro
// 3. ~100 operaciones/segundo vs ~10,000,000,000 de MD5 (con la misma GPU)
// 4. OWASP recomienda BCrypt, Argon2id o PBKDF2 para contraseñas

Pregunta 4 (Práctica) — Identificar vulnerabilidad y escribir versión corregida

Dado el siguiente código del taller, identifica la(s) vulnerabilidad(es) y escribe la versión corregida.

Código vulnerable (Sistema de Matrícula del taller): 
// AuthServlet.java — CÓDIGO VULNERABLE
@Override
protected void doPost(HttpServletRequest req, HttpServletResponse resp) {
    String usuario  = req.getParameter("usuario");
    String password = req.getParameter("password");

    // A03 — SQL Injection: concatenación directa de input del usuario
    String sql = "SELECT * FROM usuarios WHERE usuario='" + usuario
               + "' AND password='" + password + "'";

    try (Connection conn = DriverManager.getConnection(DB_URL, DB_USER, DB_PASS);
         Statement stmt  = conn.createStatement();
         ResultSet rs    = stmt.executeQuery(sql)) {

        if (rs.next()) {
            // A07 — Sin verificación de email ni cuenta activa
            // A07 — MD5 sin salt ya fue aplicado antes de llegar aquí
            req.getSession().setAttribute("usuario", usuario);
            resp.sendRedirect("dashboard.jsp");
        } else {
            resp.sendRedirect("login.jsp?error=1");
        }
    }
}
Versión corregida aplicando los mismos principios que PasajeYá: 
// AuthServlet.java — CÓDIGO CORREGIDO
@Override
protected void doPost(HttpServletRequest req, HttpServletResponse resp) {
    String email    = req.getParameter("email");
    String password = req.getParameter("password");

    // A03 CORREGIDO: PreparedStatement — el input nunca se concatena al SQL
    String sql = "SELECT id, email, password_hash, email_verificado, activo "
               + "FROM usuarios WHERE email = ?";

    try (Connection conn = DriverManager.getConnection(DB_URL, DB_USER, DB_PASS);
         PreparedStatement ps = conn.prepareStatement(sql)) {

        ps.setString(1, email);  // ← parámetro seguro, no concatenación
        ResultSet rs = ps.executeQuery();

        if (rs.next()) {
            String hashBD = rs.getString("password_hash");
            boolean emailVerificado = rs.getBoolean("email_verificado");
            boolean activo = rs.getBoolean("activo");

            // A07 CORREGIDO: verificar con BCrypt (no comparar MD5)
            BCrypt.Result result = BCrypt.verifyer().verify(
                password.toCharArray(), hashBD
            );

            // A07 CORREGIDO: verificar email y estado de cuenta
            if (result.verified && emailVerificado && activo) {
                req.getSession().setAttribute("usuario", email);
                resp.sendRedirect("dashboard.jsp");
            } else {
                // Mismo mensaje para todos los casos — no expone si el email existe
                resp.sendRedirect("login.jsp?error=credenciales_incorrectas");
            }
        } else {
            resp.sendRedirect("login.jsp?error=credenciales_incorrectas");
        }
    }
}
