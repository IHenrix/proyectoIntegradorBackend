2. HALLAZGOS DETALLADOS

SEC-2025-001 — SQL Injection en autenticación (A03:2021)

NombreSQL Injection en el flujo de login
Clasificación OWASPA03:2021 — Injection
Nivel de RiesgoCRÍTICO
URL / EndpointPOST /api/auth/login
Parámetrosemail, password (body JSON)
HerramientaAnálisis de código fuente + JUnit 5 / Mockito
EstadoCORREGIDO — JPA + BCrypt
Código vulnerable (ejemplo Sistema de Matrícula del taller): 
// AuthService.java — CÓDIGO VULNERABLE
String query = "SELECT * FROM usuarios WHERE usuario='" + usuario
             + "' AND password='" + password + "'";
// Payload: usuario = "' OR '1'='1"
// Resultado: acceso sin contraseña
Corrección en PasajeYá — AuthServiceImpl.java: 
// Spring Data JPA genera PreparedStatement internamente
Optional<Usuario> uOpt = usuarioRepo.findByEmail(emailNormalizado);
// El email es tratado como parámetro, nunca concatenado en SQL.
// La contraseña se valida con BCrypt — nunca en la query SQL:
if (!passwordEncoder.matches(dto.password(), usuario.getPasswordHash())) {
    throw new RuntimeException("Credenciales incorrectas");
}
Payload probadoResultado esperado (sistema vulnerable)Resultado en PasajeYá
' OR '1'='1HTTP 302 — acceso sin contraseñaRuntimeException: Credenciales incorrectas
' UNION SELECT NULL--Extracción de datosRuntimeException: Credenciales incorrectas
admin'--Login como admin sin passwordRuntimeException: Credenciales incorrectas
Impacto si no estuviera corregido: Un atacante podría acceder al sistema como cualquier usuario (incluyendo administradores) sin conocer la contraseña, comprometiendo los datos de vuelos y alertas de precio de todos los usuarios.

Recomendación: Mantener el uso de Spring Data JPA / PreparedStatement. Nunca construir consultas SQL concatenando input del usuario.

SEC-2025-002 — Control de Acceso Roto: endpoints privados sin token (A01:2021)

NombreAcceso a endpoints privados sin autenticación
Clasificación OWASPA01:2021 — Broken Access Control
Nivel de RiesgoCRÍTICO
URL / EndpointsGET /api/alertas, GET /api/perfil, DELETE /api/alertas/{id}
HerramientaBurp Suite Community — Repeater (petición sin cabecera Authorization)
EstadoCORREGIDO — Spring Security + JWT
Simulación con Burp Suite Repeater: 
GET /api/alertas HTTP/1.1
Host: localhost:8080
(sin cabecera Authorization)

Respuesta PasajeYá: HTTP 401 Unauthorized
{"error": "Unauthorized"}
Código vulnerable (ejemplo Sistema de Matrícula del taller): 
// MatriculaController.java — VULNERABLE
@GetMapping("/historial/{estudianteId}")
public String verHistorial(@PathVariable Long estudianteId, ...) {
    // No verifica que estudianteId == usuario en sesión
    // Cualquier usuario autenticado accede al historial de cualquier otro
    List<Matricula> historial = service.getHistorial(estudianteId);
    ...
}
Corrección en PasajeYá — SecurityConfig.java + AlertaController.java: 
// SecurityConfig.java — anyRequest().authenticated() protege todos los endpoints privados
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/auth/**", "/api/vuelos/**", ...).permitAll()
    .anyRequest().authenticated()  // JWT obligatorio para todo lo demás
)

// AlertaController.java — el email viene del TOKEN, no de la URL
@GetMapping
public ResponseEntity<List<AlertaDTO>> listar(Authentication auth) {
    // auth.getName() = email extraído del JWT por JwtFilter
    // El usuario solo puede ver SUS alertas — imposible manipular el ID
    return ResponseEntity.ok(alertaService.listar(auth.getName()));
}

SEC-2025-005 — Hash de contraseña débil: MD5 sin salt (A07:2021)

NombreContraseñas almacenadas con algoritmo inseguro
Clasificación OWASPA07:2021 — Identification and Authentication Failures
Nivel de RiesgoALTO
Columna afectadausuario.password_hash en PostgreSQL
HerramientaAnálisis de código fuente + JUnit 5
EstadoCORREGIDO — BCryptPasswordEncoder
Código vulnerable (ejemplo del taller): 
// MD5 sin salt — vulnerable a rainbow tables
public String hashPassword(String password) {
    return DigestUtils.md5Hex(password);  // ❌ inseguro
}
Corrección en PasajeYá — SecurityConfig.java: 
// BCrypt con salt automático — diferente hash en cada codificación
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();  // factor de trabajo por defecto: 10
}
// Uso en AuthServiceImpl:
usuario.setPasswordHash(passwordEncoder.encode(dto.password()));
// Verificación:
passwordEncoder.matches(dto.password(), usuario.getPasswordHash());
AlgoritmoMD5 (vulnerable)BCrypt (PasajeYá)
SaltNo tieneSalt aleatorio automático
Mismo input = mismo hashSí (rainbow tables posibles)No (cada hash es único)
Velocidad (ataque fuerza bruta)Muy rápido (~10 mil millones/s con GPU)Lento por diseño (~100/s)
Uso recomendado OWASP 2024Prohibido para contraseñasRecomendado

4. PRUEBAS CON BURP SUITE — SQL INJECTION Y BROKEN ACCESS CONTROL

Laboratorio 2 — SQL Injection en /api/auth/login (adaptado del taller): 
POST /api/auth/login HTTP/1.1
Host: localhost:8080
Content-Type: application/json

{"email": "' OR '1'='1", "password": "cualquiera", "captchaToken": "test"}

Respuesta PasajeYá:
HTTP/1.1 400 Bad Request
{"message": "Credenciales incorrectas"}
→ JPA trató el payload como dato, no como SQL. Vulnerabilidad NO presente.
Laboratorio 3 — Broken Access Control / IDOR (adaptado del taller): 
// Intento: acceder a alertas sin token
GET /api/alertas HTTP/1.1
Host: localhost:8080
(sin Authorization)

Respuesta PasajeYá:
HTTP/1.1 401 Unauthorized
→ JwtFilter rechaza la petición. Vulnerabilidad NO presente.

// Intento: usuario A intenta ver alertas de usuario B
GET /api/alertas HTTP/1.1
Authorization: Bearer <token-usuario-A>

Respuesta PasajeYá: alertas de usuario-A solamente.
El email se extrae del JWT — no hay parámetro ID manipulable en la URL.

6. CONCLUSIONES Y RECOMENDACIONES

ÁreaEstadoAcción recomendada
SQL Injection (A03)SEGUROMantener uso de Spring Data JPA. Nunca usar JDBC directo con concatenación.
Control de acceso (A01)SEGUROEl email viene siempre del JWT. Mantener anyRequest().authenticated().
Contraseñas BCrypt (A07)SEGUROConsiderar aumentar el factor de BCrypt a 12 en producción.
JWT secret en config (A02)PENDIENTEMover a variable de entorno antes del despliegue en producción.
Cabeceras HTTP de seguridad (A05)PENDIENTEAgregar X-Frame-Options, X-Content-Type-Options en SecurityConfig para producción.
Rate limiting en login (A07)PENDIENTEImplementar límite de intentos de login (bucket4j o similar) antes de ir a producción.

Conclusión general: El backend de PasajeYá tiene corregidas las 3 vulnerabilidades críticas priorizadas por el taller (A03 SQL Injection, A01 Control de Acceso Roto, A07 Autenticación Fallida). Esto se debe al uso de Spring Data JPA (PreparedStatement automático), BCryptPasswordEncoder, Spring Security con JWT y verificación de email obligatoria. Las pruebas de regresión de seguridad (15 tests JUnit) garantizan que estas correcciones no serán revertidas accidentalmente en el futuro.
